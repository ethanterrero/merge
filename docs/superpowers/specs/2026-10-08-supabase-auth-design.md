# Supabase connection and email sign-in — design

**Date:** 2026-10-08
**Status:** Approved for planning
**Scope:** Hosted Supabase project setup, profile RLS, email-code sign-in, profile creation. Commutes, discovery, and First Ride stay on mock data.

## Goals

- Connect the mobile app to the existing hosted Supabase project (`aeycmdjoplppvizvwhgs`).
- Let people sign in with a 6-digit email code and create a `profiles` row.
- Keep the app runnable as a click-through prototype when no Supabase environment is configured.

## Project setup

### Tooling

- Add the `supabase` CLI as a root dev dependency. Nothing is installed globally.
- Add `supabase/config.toml` (generated by `supabase init`).
- Root scripts:
  - `db:link`: `supabase link --project-ref aeycmdjoplppvizvwhgs`
  - `db:push`: `supabase db push`
  - `db:types`: `supabase gen types typescript --linked > apps/mobile/src/lib/database.types.ts`
  - `db:test`: `scripts/db-test.sh`

### Done by the project owner

These steps use the owner's own credentials and are not automated:

1. `npx supabase login`
2. `npm run db:link` (prompts for the database password)
3. Copy the project URL and anon key into `apps/mobile/.env` (gitignored via `.env` in `.gitignore`). Never the service-role key.
4. Supabase dashboard:
   - Authentication → Providers → Email: enabled, "Confirm email" on.
   - Authentication → Email Templates → Magic Link: the body includes `{{ .Token }}` so the email carries a 6-digit code.
   - Authentication → Email OTP expiration: 600 seconds.

### Migrations

- **`0002_profiles_rls.sql`** (new): RLS policies on `profiles`.
  - `select`, `insert`, `update` where `id = auth.uid()`, for the `authenticated` role.
  - No `delete` policy. A profile is removed by the `on delete cascade` from `auth.users`.
  - `display_name` check: 2–40 characters after trimming.
  - All other tables remain default-deny.
- The First Ride migration is renumbered to **`0003_first_ride.sql`**.

Before `db:push` runs against the hosted database, the exact list of pending migrations is shown to the project owner, and the push waits for explicit approval.

### Types

`db:types` generates `apps/mobile/src/lib/database.types.ts`. `lib/supabase.ts` becomes `createClient<Database>(…)`.

### Supabase MCP (developer tooling)

A user-scoped, read-only Supabase MCP server (`docs`, `database`, `debugging`, `development`) is configured on the owner's machine, not in the repo. It's used to inspect the live schema and run security advisors. Migrations are never applied through it, because `supabase/migrations/` is the source of truth.

## App

### Two modes

| `.env` | Mode | Behavior |
| --- | --- | --- |
| URL or anon key missing | `prototype` | Today's click-through prototype. No sign-in. |
| Both set | connected | Sign-in required before onboarding continues. |

### `state/auth.tsx`

`AuthProvider` wraps the app (outside `CommuteProvider`) and exposes:

- `status`: `loading` | `signedOut` | `needsProfile` | `ready` | `prototype`
- `session`, `profile`
- `sendCode(email)`: `supabase.auth.signInWithOtp({ email, options: { shouldCreateUser: true } })`
- `verifyCode(email, code)`: `supabase.auth.verifyOtp({ email, token: code, type: 'email' })`
- `saveProfile({ displayName, role })`: upsert into `profiles` with `id = session.user.id`
- `signOut()`

It subscribes to `onAuthStateChange` and fetches the profile whenever a session appears. Sessions persist through the existing SQLite-backed `localStorage`.

### Flow

1. **Welcome** (unchanged position): intro and role choice → Continue.
2. **Sign in** (`signIn`, new): email field, "Send code". Copy: "We'll email you a 6-digit code. No password needed."
3. **Enter code** (`verifyCode`, new): 6-digit field (`textContentType="oneTimeCode"`, `autoComplete="one-time-code"`, numeric keyboard). "Resend code" enabled after 60 seconds. "Use a different email" returns to step 2.
4. **Your name** (`profileName`, new; only when no profile exists): "What should riders call you?" Hint: "First name and last initial, like Priya S." Saves `display_name` and the Welcome role.
5. Continue to Where and when → Preferences → Discover (mock data).

Launch routing:

- `loading`: a branded loading screen.
- `signedOut`: Welcome.
- `needsProfile`: Welcome, and Continue goes straight to Your name.
- `ready`: Discover (commute values are the mock defaults until commutes are saved).
- `prototype`: Welcome, with today's flow.

Within a session, Welcome's Continue goes to Sign in when `signedOut`, to Your name when `needsProfile`, and to Where and when when `ready` or `prototype`.

**Sign out:** an account button in the Discover header opens a sheet showing the signed-in email and "Sign out". Signing out returns to Welcome. Hidden in prototype mode.

### Errors

| Case | Behavior |
| --- | --- |
| Malformed email | Inline message, nothing sent |
| Send rate-limited (HTTP 429) | "Too many codes requested. Try again in a few minutes." |
| Other send failure | "Couldn't send the code. Check your connection and try again." |
| Wrong or expired code | "That code didn't work. Check it or request a new one." (does not distinguish wrong from expired) |
| Profile save fails | Stay on Your name with the text kept, and show Retry |
| Session refresh fails / signed out elsewhere | `onAuthStateChange` → `signedOut` → Welcome |

## Testing

- `npm run typecheck` passes.
- **`scripts/db-test.sh`:** starts a throwaway `postgis/postgis` container, applies a minimal auth shim (`auth` schema, `auth.users`, `auth.uid()` reading `request.jwt.claim.sub`, the `anon` and `authenticated` roles), applies every file in `supabase/migrations/` in order, then runs every `supabase/tests/*_test.sql`. Test files are plain SQL with `DO` blocks that `raise exception` on failure. First Ride's tests reuse this harness.
- **`supabase/tests/profiles_test.sql`** asserts:
  1. A user can read and update their own profile.
  2. A user cannot read another user's profile.
  3. A user cannot insert a profile with another user's `id`.
  4. `anon` cannot read any profile.
  5. `display_name` outside 2–40 characters is rejected.
- **After the hosted push:** run the security advisors and `list_tables` through the read-only MCP. Expect no "RLS disabled" findings and a schema matching the migration files.
- **Manual end-to-end** (Expo web build, hosted project, owner's own email):
  1. New user: Welcome → Sign in → code → Your name → Where and when.
  2. Reload: still signed in, lands on Discover.
  3. Wrong code: shows the error.
  4. Sign out: returns to Welcome.
  5. Returning user: sign in → Discover.
  6. With `.env` removed: prototype mode works as before.

## Docs

- **`README.md`, Getting started:** the `.env` values, `db:link`, `db:push`, the dashboard settings above, and the built-in email sender's limits (delivers only to project team members, low hourly limit).
- **`docs/ui.md`:** the sign-in steps and the two modes.
- **`docs/mvp.md`, pilot blockers:**
  - Custom SMTP (e.g. Resend or Postmark), so codes reach testers outside the Supabase team.
  - In-app account deletion, required by App Store guideline 5.1.1(v) for apps that support account creation.
- **First Ride spec:** migration renamed to `0003_first_ride.sql`. Its tests use `scripts/db-test.sh`.

## Out of scope

- Saving commutes (needs a privacy design for exact origin and destination points).
- SMS, Google, and Apple sign-in.
- Configuring custom SMTP.
- Account deletion UI (listed as a pilot blocker).
- Richer profiles (photo, bio, employer, interests).
