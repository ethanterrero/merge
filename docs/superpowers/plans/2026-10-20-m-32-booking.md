# M-32 Booking Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the booking half of the approved booking spec: the driver's `confirm_ride`, the participant-only pickup reveal, `cancel_ride`, `cant_drive` (with a recorded day off), `driver_day`, and safety and account-deletion cancellations, in `0018_booking.sql`.

**Architecture:** One migration adds the ride cancel columns, a server-only `ride_pickups` table and an owner-readable `driver_days_off` table, then definer RPCs that read the caller's invitation projection (M-27's `invitation_state`) and serialize on per-person-per-date advisory locks. Clients still never write `rides`; they read it through column grants that leave out every cancel column.

**Tech Stack:** Postgres 17 + PostGIS 3.5 (hosted Supabase), plpgsql, the SQL test harness in `scripts/db-test.sh` (CI `database` job only; no local Docker).

**Spec:** `docs/superpowers/specs/2026-10-10-booking-design.md`, section 9 (plus sections 2, 6, 7 and the M-27 build notes). Owner decisions D-02, D-06, D-16 (Decided 2026-10-08), Q1–Q12 approved 2026-10-10.

- Test style: `supabase/tests/invitations_test.sql` (one transaction, `DO` blocks that `raise exception`, `tests.as_user/as_anon/as_admin`, `pg_temp` helpers). Booking ids end in `32xx` (`'00000000-0000-0000-0000-0000000032' || n`), deletion-test ids in `33xx`.

## Locking (why the sequential tests are enough)

Every path that changes a person's rides on a date takes that person's day lock, `pg_advisory_xact_lock(hashtextextended('merge.day:' || uid || ':' || ride_date, 0))`. `confirm_ride` takes, always in this order: both profiles `for share` (id order; serializes with a suspension's `for no key update`), the pair lock `merge.pair:{lo}:{hi}` (serializes with a block's triggers and with send), both day locks (uuid order), then the invitation row `for update`, and only then recomputes the projection and counts seats. Two confirms for one driver and date queue on the driver's day lock; the second one reads the first one's committed ride (read committed takes a fresh snapshot per statement) and its invitation already closed `full`, so it is refused. `cancel_ride` takes both day locks (uuid order) before the ride row; `cant_drive` takes the driver's day lock before touching rides or invitations. The day locks come before any invitation row lock everywhere, so `cant_drive` (day lock → invitation rows) can't deadlock with a confirm. The partial unique index on `(passenger_id, ride_date)` is a backstop for the passenger rule. The harness can't run two sessions, so tests show each refusal sequentially.

## Review Focus

1. A passenger confirmed by one driver while another driver's request to them is open: the other driver's confirm must be `unavailable`, never a second ride (tested in Task 1, Q1 group).
2. A "Both" member booked as a passenger trying to confirm as a driver the same date: `already_booked` (Task 1).
3. A spot inside the area but farther than 402 m from the passenger's exact point: accepted, proving the check uses the copied area (Task 1, spot group).
4. The other participant reading `rides` after a safety cancellation: sees `status = 'cancelled'` but has no privilege on `cancel_reason`, `cancelled_by`, `cancelled_at`, `cancelled_late` (Task 1, safety group).
5. A driver on a recorded day off: absent from passengers' `find_matches` for that date only, and a request to them is `unavailable` (Task 2, cant_drive group).
